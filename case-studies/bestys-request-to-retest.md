# BestYs: User Requests and Retesting

> `[SANITIZED WORK CASE]` · Technical Support and QA Tester

## Context and confidentiality

I supported an EdTech web product and live olympiad sessions. The real product, users, internal tickets, environments, and event data are not published here.

## My role

I worked at the intersection of technical support and QA: accepted user requests, clarified the expected behaviour, reproduced issues where possible, documented the scenario for the team, and checked the result after a change.

## How I worked with a request

1. Captured the user-visible problem and the context needed to reproduce it.
2. Clarified the affected role, product flow, expected result, and urgency.
3. Investigated the UI and browser/network behaviour; used API documentation or request inspection when relevant.
4. Created or clarified a task in Jira or Trello with reproduction steps, expected/actual behaviour, and impact.
5. Performed focused functional, smoke, or regression checks after a change.
6. Reported the retest result and any remaining risk to the team.

## What I passed to the team

- A short, reproducible user scenario rather than an unstructured message.
- Preconditions, steps, actual result, expected result, and relevant browser/API observations.
- Affected flow and edge cases worth checking before release.
- A clear retest status; I did not mark a change as verified without checking it.

## Tools and methods

`Jira` · `Trello` · `TestRail` · `Chrome DevTools` · `Postman` · `Swagger` · manual functional, smoke, regression, and UI testing.

## What is not published

I do not publish user records, event data, private URLs, credentials, raw tickets, screenshots, or internal release discussions. This case is a description of the workflow and responsibilities, not a claim of a public production artefact.
